1. Introduction
-------------------------------------------------------------------------------

  What is free software? When the license offers freedom to:
  - run the software for any purpose
  - study the software and change it
  - redistribute copies
  - redistribute modified copies

  Why Linux for embedded?
  - reuse components, focus on added value instead of basics
  - low cost, no per-unit royalties, no costly dev tools
  - full control, no vendor lock-in
  - easy testing
  - high-quality foundations
  - security, all sources traceable for vulnerability analysis
  - community support
  - possibility to collaborate

  Many architectures supported: x86, x86-64, ARM, RISC-V, PPC, MIPS, etc.
  - no MMU supported but with limitations
  - no 8 or 16 bit support
  - other than toolchain, bootloader and kernel other components are architecture
    independent

  RAM: at least 8MB of RAM but usually at least 32MB.

  Storage: usually more than 4MB, can be achieved with block storage (SD/MMC/
    eMMC/USB/SATA) or raw flash (NAND, NOR)

  Communication buses and systems:
  - I2C, SPI, 1-wire, SDIO, PCI, USB, CAN
  - Ethernet, Wifi, Bluetooth, etc...
  - Extensive networking support, IPv4, IPv6, TCP, UDP, firewalling, etc.

  Basic architecture:

    Dev PC (host)               Embedded System (target)
    +-----------------+   +------------------------------------+
    |                 |   | Userspace                          |
    |  +-----------+  |   |   [  Apps  ]    [  Apps  ]         |
    |  | Tools     |  |   |   [  Libs  ]    [  Libs  ]         |
    |  | compiler  |  |   |        [ C library ]               |
    |  | debugger  |  |   +------------------------------------+
    |  | ...       |  |   | Linux kernel                       |
    |  +-----------+  |   |   [Task/Mem]    [ Drivers ]        |
    |                 |   |   [Network ]    [ FileSys ]        |
    |                 |   +------------------------------------+
    |                 |   | - - - - - Bootloader - - - - - - - |
    |                 |   +====================================+
    |                 |   |              Hardware              |
    +-----------------+   +------------------------------------+

    - BSP contains a bootloader and kernel with suitable device drivers for a
      target (Kernel Development course)
    - Integrate bootloader, kernel, 3rd party libraries, applications, etc into
      a system (this course)

3. Cross-compiling toolchains
-------------------------------------------------------------------------------

  The preinstalled tools available in a Linux workstation are usually native
  toolchains - they compile binary code for the workstation arch (x86).

  Cross-compiling makes sense because the host is powerful and the target is
  very resource constrained:
     Compile code in host ---> run binary in target

  Build mechanisms on Linux often rely on a architecture tuple,
    1: architecture name
    2: vendor name (optional)
    3: target OS or none, if not targeting an operating system
    4: ABI/C library
      e.g.:
        - arm-linux-gnueabihf
        - mips64el-linux-gnu
        - arm-vendor-none-eabihf

      Tuple can be used as prefix to differentiate from native toolchain:
        - gcc                     --> native compiler
        - arm-linux-gnueabihf-gcc --> cross compiler

  A GCC toolchain contains:

              +---------------------------------------------+
              |                                             |
              |  +-----------------+   +-----------------+  |
              |  |    Binutils     |   | Kernel headers  |  |
              |  +-----------------+   +-----------------+  |
              |                                             |
              |  +-----------------+   +-----------------+  |
              |  | C/C++ libraries |   | C/C++ compiler  |  |
              |  +-----------------+   +-----------------+  |
              |                                             |
              |  +-----------------+                        |
              |  |  GDB debugger   |                        |
              |  |   (optional)    |                        |
              |  +-----------------+                        |
              |                                             |
              |                 Cross-compilation toolchain |
              +---------------------------------------------+

    - binutils: set of tools to generate and manipulate binaries, for example:
      - ld linker
      - as assembler
      - ar archiver
      - objdump, readelf, size, nm, strings to inspect binaries
      - objcopy to modify binaries
      - strip to remove parts of binaries only needed for debugging

    - kernel headers:
      - the C library and applications need need to interact with the kernel:
        system calls, constants, data structures, etc.
      - compiling the C standard library or applications requires kernel headers
      - available in
        - linux/
        - asm/
        - arch/<arch>/include/uapi
        - include/uapi
      - extracted from the kernel sources using a Makefile target "headers_install"
      - usually backwards compatible, to not break old programs when the kernel is
        updated - updating a kernel shouldn't break existing programs

                        +-----------------------------+
                        |         Application         |
                        +-----------------------------+
                             |                  |
                             v                  |
                        +---------+             |
                        |C library|             |
                        +---------+             |
                             |                  |
                        -----|------------------|------
                             v                  v
                          +------------------------+
                          |     Kernel headers     |
                        +-+------------------------+-+
                        |           Kernel           |
                        +----------------------------+

    - C/C++ libraries:
      - essential component of the system:
        - sits and interfaces between applications and kernel
        - provides well known standard C API to ease development
      - examples: glibc, musl, uClibc...
        - https://www.gnu.org/software/libc/
        - different advantages, e.g. licensing or size
      - the cross-compiling toolchain is compiled against a specific C std lib

    - C/C++ compiler:
      - GCC, GNU compiler collection
      - Famous free compiler, can do many languages and many architectures

    - GDB debugger (maybe)

  A Linux toolchain
    - includes a Linux-ready C standard library, that knows how to perform
     system services via system calls.
    - can be used to build Linux applications or bare-metal code (super set)
    - the tuple includes "linux", e.g. arm-none-linux-gnueabihf

  A bare-metal toolchain:
    - does not include a C standard library (or only a minimal one)
    - can only build bare-metal code (subset)
    - the tuple includes "none", e.g. arm-none-none-eabi

  When building a toolchain, the ABI must be understood:
    - application binary interface, contains e.g. calling conventions and
      organization of structs
    - e.g on ARM EABI, EABIhf, on RISC-V ilp32, ilp32f, etc.

  Building a toolchain is difficult. The typical process is:
    - build dependencies of binutils/gcc
    - build binutils
    - build a baremetal, first stage GCC
    - extract kernel headers from the Linux source code
    - build the C library using the first stage GCC
    - build the second state and final GCC supporting linux and C library
    Reference: https://crosstool-ng.github.io/docs/toolchain-construction/

  You can download pre-built toolchains but that's less flexible

  You can also use utilities that automate the process, e.g using scripts,
    Makefiles, etc.
    - examples: Crosstool-ng, OpenEmbedded / Yocto Project

  Once built, the toolchain will contain:
    - bin/, the cross compilation tool binaries
    - <arch-tuple>/sysroot:
      - <arch-tuple>/sysroot/lib : C lib, GCC runtime, C++ std lib for the target
      - <arch-tuple>/sysroot/usr/include: C lib headers, kernel headers

4. Bootloaders and firmware
-------------------------------------------------------------------------------

  Bootloader is responsible for:
    - hardware initialization
    - loading an application binary (kernel) from flash, network or storage
    - optionally decompression
    - execute

  Usually contain a shell or menu for user to select or diagnose stuff.

  x86:
    - BIOS, stored in flash, closed source
    - Storage devices contain a first sector called MBR, master boot record
      Contains a partition table and 446 bytes of bootloader code

          BOOT PROCESS
          +------+   +---------+   +---------+   +--------+
          | BIOS |-->| STAGE 1 |-->| STAGE 2 |-->| KERNEL |
          +------+   +---------+   +---------+   +--------+
            ROM        Raw Disk      Raw Disk      Filesys
          (init       (runs in      (runs in      (runs in
            RAM)        RAM)          RAM)          RAM)

          STORAGE LAYOUT (USB, SATA, SD, eMMC)
          +-+----------+-------------------------+-------------------+
          | | Stage 2  | Regular partition       | Regular partition |
          | | ~100s KB |Linux FS, Kernel, root FS|                   |
          +-+----------+-------------------------+-------------------+
          |-'
          v
          +-------------+----------+
          | Stage 1     | Part.    |
          | (446 bytes) | Table    |
          +-------------+----------+
                Sector 0 (MBR)

    - From 2006, UEFI started replacing BIOS, also stored in flash
      Loads EFI binaries from the EFI system partition (e.g. a bootloader)
        - the EFI system partition is a special partition
        - formatted with FAT file system
        - /efi/boot/bootx32.efi

          BOOT PROCESS
          +----------+   +------------+   +--------+
          |   UEFI   |-->| Bootloader |-->| Kernel |
          +----------+   +------------+   +--------+
            (ROM/        (from EFI PT,    (from FS,
            flash)        runs in RAM)     runs RAM)

          STORAGE LAYOUT (USB, SATA, SD, eMMC, etc.)
          +-----------+----------------------+--------------------------+
          | Partition | EFI System Partition | Regular partition        |
          | table     | (FAT filesystem)     | (Regular Linux FS)       |
          |           | /efi/boot/*.efi      | Kernel + root FS         |
          +-----------+----------------------+--------------------------+

            Disk model: SKHynix_HFS256GD9TNI-L2B0B

            /dev/nvme0n1p1    2048   2203647   2201600     1G EFI System

    - ACPI is an open standard for OSs to discover and configure HW components,
      manage power, status monitoring, etc.
      Tables provided by the firmware for the OS to use
      (Advanced Configuration and Power Interface)

    - Some effort for adoption outside the x86 world. ARM working on this. RISCV
      also shows some effort to use UEFI and ACPI.

  Embedded:
    - Most SoCs come with a small ROM containing code that cannot be changed
    - Usually finds a bootloader in flash or from a USB or eMMC, loads it and
      runs it
      - usually in 2 stages:
        1st stage: small, in internal SRAM, initializes external DRAM
          step 1: ROM code loads the first stage from eMMC and executes in
            internal SRAM
          step 2: the first stage bootloader configures the DDR controller
          step 3: the first stage bootloader loads the second stage into external
            DDR and executes it
        2nd stage: runs from external DRAM

    - The datasheet can provide information on bootmodes, which pins need to be
      high or low
      - example on the BBB: chapter 26

  Bootloaders:
    - GRUB (grand unified bootloader)
      - from GNU
      - de-facto standard for most Linux distros in x86
      - can read many filesystems
      - provides menu and shell
      - can load over network too
    - Syslinux:
      - for network or removable media
      - a bit rustic, not very maintained
    - systemd-boot:
      - simple UEFI boot manager
      - good alternative to GRUB for UEFI systems
    - shim:
      - minimal UEFI bootloader
      - signed by Microsoft, used for secure boot
      - can chainload another bootloader or the kernel directly
    - U-boot:
      - defacto standard for embedded systems
      - supports ARM, ARM64, RISC-V, PPC, MIPS, etc.
      - supports x86 with UEFI too
      - https://www.denx.de/wiki/U-Boot

  Trusted firmware:
    - Usually the bootloader is discarded from RAM after booting
    - But when running security mechanisms, some trusted firmware remains
      - usually stored in DDR or some specific SRAM accessible by OS
      - provides services to the OS, implemented by the secure firmware
      - prevents the OS accessing critical HW resources
    - in RISCV that trusted FW can be the OpenSBI
    - in ARM that trusted FW can be the Secure Monitor in EL3

    - in RISC-V:
      3 privilige levels:
        - M-mode: machine mode, like a secure mode
        - S-mode: supervisor mode, at which linux kernel runs
        - U-mode: user mode, at which linux user space apps run
      SBI is the supervisor binary interface, a standardize interface between
        OS and firmware
        There is a reference open source implementation called OpenSBI:
        https://github.com/riscv-software-src/opensbi


                                        SBI calls
                                     +------------------------+
                                     v                        |
          +------+  +----------+  +---------+  +------+  +----------+    +----------+
          | ROM  |->|1st Stage |->| OpenSBI |->|U-Boot|->|  Linux   |<-->|Userspace |
          | Code |  |Bootloader|  |         |  |      |  |  Kernel  |    |   Apps   |
          +------+  +----------+  +---------+  +------+  +----------+    +----------+
            M-mode     M-mode        M-mode      S-mode      S-mode          U-mode
                                  (resident)              (resident)


    - in ARM:
      4 privilige levels:
        - EL0: user space (untrusted)
        - EL1: kernel space (trusted)
        - EL2: hypervisor, virtualization
        - EL3: highest privilige, runs secure firmware

      2 worlds:
        - normal, for a general purpose OS like Linux
        - secure, for a separate, isolated OS and apps - TrustZone by ARM

        EL3 exists only in secure
        EL2 exists in normal and secure since ARMv8.4
        EL1/0 exists in normal and secure

        Non-secure                            Secure

            +-------+-------+-------------+   +--------------------+
        EL0 |AArch32|AArch64| AArch32 App |   |  Trusted Services  |
            |  App  |  App  |             |   |                    |
            +-------+-------+-------------+   +--------------------+
        EL1 | AArch64 Kernel|AArch32 Kern.|   |     Trusted OS     |
            +---------------+-------------+   +--------------------+
        EL2 |         Hypervisor          |   | Trusted Part. Mgr* |
            +-----------------------------+   +--------------------+
        EL3 |             Firmware / Secure Monitor                |
            +------------------------------------------------------+

      The way to interface with the secure trusted firmware is via standardized
      services, defined by ARM

        +-------------+  Linux sys  +-------------+ PSCI, SCMI, +-------------+
        |  Linux app  |    calls    |Linux kernel |    etc.     |  Secure FW  |
        |    (EL0)    |------------>|    (EL1)    |------------>|    (EL3)    |
        +-------------+             +-------------+             +-------------+


      - PSCI (power state coordination interface) e.g. power management related
        stuff like turning CPUs on and off, platform shutdown, generate resets
          https://developer.arm.com/documentation/den0022/fb/?lang=en
      - SCMI (system control and management interface) e.g. access to power domain,
        clocks, sensor, performance...
          https://developer.arm.com/documentation/den0056/latest
      - TF-A is a reference implementation of secure world software for ARMv7A
        and v8A. Includes a secure monitor that runs at EL3.
        (formerly known as ATF)
          https://www.trustedfirmware.org/projects/tf-a/ -> check the functions,
          defines, etc. this needs porting for each hardware.
      - TEE is the trusted execution environment, the secure world where a
        trusted OS can run.
        - isolated from linux
        - allows to run trusted applications and services
        - can provide services to Linux applications
        - most famous open source implementaion: https://www.op-tee.org/

          What executes when and at which level?

          TIME ---->

            SECURE  EL0 |                               (Trusted applications)
            WORLD   EL1 |                           (Trusted Execution Environment BL32)
          --------------+--------------------------------------------------
                    EL3 | [ROM BL1] [1st stage BL2] [      Secure monitor BL31      ]
          --------------+--------------------------------------------------
                    EL2 |                           [2nd stage BL33]  (Hypervisor)
            NORMAL  EL1 |                                             [Linux kernel]
            WORLD   EL0 |                                                 [Linux applications]

          Key:
          [ ] = Mandatory component
          ( ) = Optional component


  Some examples of boot sequences in ARM

    BBB, ARMv7, Cortex A8:
      1. ROM code is executed
      2. U-Boot SPL is loaded from a file called MLO in FAT filesystem in the
        first bootable partition, executes from SRAM
      3. U-Boot is loaded from a file called u-boot.img in a FAT filesystem,
        executes from DRAM
      4. Linux kernel

      Note: SPL = secondary program loader, a small, lightweight initial-stage binary
        see below

  U-Boot

    - Source here: https://elixir.bootlin.com/u-boot/v2026.07/source/

    - Configurable based on kconfig from the Linux kernel
      - Configuration files for platforms can be found here
        https://elixir.bootlin.com/u-boot/v2026.07/source/configs
          - define CPU, drivers needed, features switched on, etc.
      - Note: migration to kconfig ongoing - some configuration files still in
        include/configs headers and defconfig files
        Example stm32mp15_trusted_defconfig:
          CONFIG_ARM=y
          CONFIG_ARCH_STM32MP=y
          CONFIG_TFABOOT=y
          CONFIG_SYS_MALLOC_F_LEN=0x3000

      - Similarly to Crosstool-ng, we have to configure and then build (compile)
        - load a pre-defined configuration with make NAME_defconfig
        - run make menuconfig to further customize the Uboot

      - We need to specify the path to the cross-compiler at some point
        - env var CROSS_COMPILE contains the prefix common to all cross-compilation
          tools, example:
            $ export PATH=$PATH:/my/path/to/toolchain/bin
            $ make CROSS_COMPILE=arm-linux-   [adding the path keeps CROSS_COMPILE short]

      - Result is a u-boot.bin file, the U-boot image. It can have other formats
        for other boot media like NAND or eMMC

      - SPL is a very stripped down version of U-boot, no shell, no commands
        - small enough to meet the constraints of first-stage bootloader (should
          fit in SRAM)
        - also configured via menuconfig

    - Device trees are structures that describe the topology of the hardware
      - software ---  gets to know --> hardware
      - mainly used by Linux but now also by U-boot
      - .dts files exist for each board (create one for a new board)
      - defconfigs usually specify a default device tree, can be override with
        DEVICE_TREE variable

      example BBB:
        - there is one defconfig file for TI AM335x platforms
            config/am335x_evm_defconfig
        - contains a default device tree for the TI EVM
            arch/arm/dts/am335x-evm.dts
        - but there is a device tree file describing the BBB:
            arch/arm/dts/am335x-boneblack-wireless.dts

        - so now we configure and build
           $ export PATH=/path/to/toochain/bin
           $ make am335x_evn_defconfig
           $ make DEVICE_TREE=am335x-boneblack-wireless CROSS_COMPILE=arm-linux-

        - now we set out device tree and our cross-toolchain
        - it will produce:
          1. first stage SPL called MLO (mmc load) required by TI platforms
          2. u-boot.img, full U-boot, second stage bootloader

    - Most U-boot configuration happens at compile time in menuconfig
      - it's also possible to have runtime configuration via environment variables
        located in RAM
      - the environment can be in a fixed offset in NAND or MMC/USB, in a file on
        FAT or EXT4, or none at all...

    - How to manipulate the environment, read, write, debug and boot:
        see cheat sheet for important commands!

    - U-Boot offers the concept of FIT image, multiple things into one image
      https://www.thegoodpenguin.co.uk/blog/u-boot-fit-image-overview/
      - contains multiple kernel images
      - contains multiple device trees
      - contains multiple initramfs
      - ensures binaries don't overlap in memory
      - useful for secure booting too
      - u-boot knows how to find different things inside

    - A "generic distro boot" can be used - it asks for a few variables and then
      boots
      https://u-boot.readthedocs.io/en/latest/develop/distro.html
      - kernel_addr_r : address in RAM to load the kernel image
      - ramdisk_addr_r : address in RAM to load the initramfs image
      - fdt_addr_r : address in RAM to load the flattened device tree
      - pxefile_addr_r : address in RAM to load the configuration file (below)
      - bootfile : path configuration file e.g /boot/extlinux/extlinux.conf


  TF-A: ARM trusted firmware

    - FIP = firmware in package, a concept specific to TF-A
    - Similar to FIT, a format to pack several images into a binary
    - Used to bundle BL33 (see above)

    - TF-A is not configured using kconfig
      - entirely based on variables passed on the make cmd line
      - Documented here: https://trustedfirmware-a.readthedocs.io/en/latest/getting_started/build-options.html
        for example:
        - CROSS_COMPILE : prefix for cross-compiler
        - ARCH : CPU architecture, e.g. aarch32 or aarch64
        - ARM_ARCH_MAJOR, 7 for ARMv7, 8 for ARM v8...
        - DTB_FILE_NAME : path to device tree that describes the board
        - BL33 : path to second stage bootloader, usually U-boot

    - The result of the build are, amongst others:
      - TF-A itself, e.g. tfa-a-stm32mp157a-dk2.stm32
      - the FIP image, containing UBoot, e.g. fip.bin

5. Linux Kernel intro
-------------------------------------------------------------------------------

  The kernel sits between libraries/user apps and the hardware.

  +-------------------+   Call to    +----------+   Manage   +----------+
  |    [User app B]   |   services   |          |  hardware  |          |
  | [Library A][App A]|------------->|  Linux   |----------->|          |
  |    [C library]    |<-------------|  kernel  |<-----------| Hardware |
  +-------------------+ Event notif.,+----------+   Event    +----------+
                        info exp.                  notif.

  The linux kernel main roles are:
    - managing the hardware resources, CPU, memory, IO, etc.
    - provide a set of hardware and architecture independent APIs to allow the
      user and libraries to access applications
    - handle concurrency and usage limits of hardware, e.g. different apps trying
      to use a single network interface

  System calls:
    - main interface between kernel and user space
    - about 400!
    - file and device operations, networking operations, IPC, process management,
      memory mapping, timers, threads, etc.
    - system calls are wrapped by the C library. user space applications use the
      C library function instead of a direct call

  Linux makes system and kernel information available via pseudo-filesystems:
    - proc mounted on /proc: OS related info
    - sysfs mounted on /sys: system representation as a device tree

  Linux is released officially every 10 weeks. Each stable branch has a 2 week
  merge window and 6 to 10 week bug-fixing period - after this a new stable
  branch happens.
    - LTS releases also get latest security and bug fixes (for at least 2 years)
    - Some commercial distributios have much longer support, e.g. Wind River Linux

    - Mainline versions, released by Linus Torvalds:
    https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git

    - Stable versions, released by maintainers group:
    https://git.kernel.org/pub/scm/linux/kernel/git/stable/linux.git

  Many semiconductor vendors supply their own Linux sources:
    - focus on HW support first
    - suitable for PoCs
    - may break support for other platforms/devices : not important

  Complete kernel sources:
    https://kernel.org/pub/linux/kernel
    but nowadays most people just use Git

    Going through the sources: https://elixir.bootlin.com

  Kernel configuration:
    - the process of defining which options the kernel should be compiled with
      depends e.g. on architecture or capabilities you might want

    - happens via Makefiles
    - you need to define architecture via ARCH and the toolchain via CROSS_COMPILE.

    - Initial kernel configuration ideas:
      - Desktop or server: copz from /boot/config-`uname -r`
      - Embedded: defaults stored in arch/<arch>/configs -> you'll see many defconfigs

    - A tool like make menuconfig aids making changes.
      - Configuration is overwritten to file .config
      - It's possible to save your configuration in a defconfig file
      - store in arch/<arch>/configs/myown_defconfig so that you can "make" with it

  Kernel image:
    - a single file, resulting from linking all object files
    - loaded into memory by the bootloader
    - all features available as soon as kernel starts

  Kernel modules:
    - device drivers, file systems can be compiled as modules
    - loadable dynamically
    - stored as a separate file in a filesystem (so fs is mandatory to use modules)

  Types of kernel options:
    - bool (include/exclude)
    - tristate (include in image/include as module/exclude)
    - int
    - hex
    - string

  Dependencies:
    - config B depends on A : B is not visible until A is enabled
    - config A select B : when A is enabled, B is enabled too (cannot be disabled manually)

  xconfig:
    - GUI to configure the kernel
    - easy to load files, serach, etc

  make menuconfig:
    - similar in style to UBoot

  Frequent problem: revert to an old configuration. Solution: use .config.old as
  back up copy that you can copy to .config

  Kernel compilation:
  - make only works at top level directory
  - make -j<n> distributes the build job through multiple threads

  Faster recompilation can be achieved by using the ccache compiler cache:
  export CROSS_COMPILE="ccache arm-linux-"

  Compilation results:
  - arch/<arch>/boot/Image, uncompressed kernel image, bootable
  - arch/<arch>/boot/*Image*, compressed kernel image, bootable
    - bzImage: x86
    - zImage: ARM
    - Image.gz: RISCV
    - vmlinux.bin.gz: ARC, etc...
  - arch/<arch>/boot/dts/<vendor>/*.dtb, compiled Device Tree Blobs
  - .ko files are Kernel Modules and are spread over the source tree
  - vmlinux is a raw, uncompressed kernel image in ELF format, for debugging purposes
    (not booting)

  Native kernel installation
  - sudo make install: installs by default in the host system
    - installs /boot/vmlinuz-<version>, the compressed kernel image, same as in
      arch/<arch>/boot/
    - installs /boot/System.map-<version>, stores symbol addresses for debugging
      purposes (obsolete)
    - installs /boot/config-<version>, kernel configuration
    - reruns bootloader configuration utility to make new kernel available in
      the next boot

  Embedded kernel installation
  - make install rarely used in embedded
    - kernel image is single file
    - there is no way to deploy and load kernel image for all targets

  Native module installation
  - sudo make modules_install: installs modules by default in host system
    - installs all modules in /lib/modules/<version>/
      - kernel/, module .ko files
      - modules.alias or modules.alias.bin, aliases for module loading utilities
      - modules.dep or module.dep.bin, module dependencies
      - module.symbols or module.symbols.bin, tells which module a given symbol
        belongs to
      - modules.builtin, list of build-in modules of the kernel

  Embedded module installation
  - can't directly use make modules_install because it would install the modules
    in /lib/modules (the host fs not target fs)
    - INSTALL_MOD_PATH variable is needed to generate the module related files
      and install the modules in the target root fs instead of host root fs
      make INSTALL_MOD_PATH=<dir>/ modules_install

  Clean up targets for kernel make:
    (remember that the instructions of make are called targets)
  - clean: Remove most generated files but keep the config and enough build
    support to build external modules
  - mrproper: Remove all generated files + config + various backup files
  - distclean: mrproper + remove editor backup and patch files
  or, if on git, simply "git clean -fdx"

  Hardware description:
  - embedded architectures have a lot of non-discoverable devices, serial ports,
    ethernet, i2c, nand flash, usb controllers, etc.
  - description of the hardware to the kernel can be made via:
    - x86: ACPI tables
    - most embedded devices: OpenFirmware Device Tree (DT)

  Device trees:
  - developers write Device Tree Sources, which compile to Device Tree Blobs
    DTS ---compilation---> DTB
  - there is one device tree per board/platform
  - can be found in arch/<arch>/boot/dts/<vendor>/<board>.dtb
  - the user may customize to add external devices, configure pin muxing or
    system parameters like flash partition

  Booting via Uboot:
  - ARM32
    - Boot zImages files via command bootz
  - ARM64 or RISCV
    - Boot Image files via command booti
  - UBoot should also pass a DTB to the kernel:
  Typical flow:
  1. load zImage to address X
  2. load <board>.DTB at address Y
  3. boot[z|i] X - Y
      (- indicates no initramfs)

  Kernel command line
  - adjusts kernel behaviour without recompilation
  - arguments very important for system configuration
    - root= for root file system
    - console= destination of kernel messages
    - many more: https://www.kernel.org/doc/html/latest/admin-guide/kernel-parameters.html

  Kernel log
  - messages are kept in a size adjustable (CONFIG_LOG_BUF_SHIFT) buffer
  - dmesg displays the available kernel log messages

6. Linux Root Filesystem
-------------------------------------------------------------------------------

  Filesystems:
    - used to organize data in directories and files
    - in UNIX, applications see a single global hierarchy of dirs and files,
      can also be composed of several filesystems
    - filesystems are mounted in a specific location (mount point)
    - mount points allow applications to access files, regardless of actual
      physical storage location

  Root filesystem:
    - a particular filesystem mounted at the root of the hierarchy, identified
      by /
    - mount and umount are programs, so files inside the root filesystem
    - the root fs is the first mounted file system, mounted by the kernel
    - kernel option root=
    - kernel panics without a root fs (as seen in the lab)
    - can be mounted from USB key, hard disk, SD card, NAND flash, NFS protocol,
      etc...

  Mounting rootfs from storage devices:
    - Hard disk or USB key:
      root=/dev/sdXY, X is a letter for the device, Y a number for the partition
    - Partitions of a SD card:
      root=/dev/mmcblkXpY, X device, Y partition
    - Flash storage:
      root=/dev/mtdblockX, X partition number

  Mounting rootfs from network:
    - root=/dev/nfs
    - the rootfs could be a directory in the host Linux machine, exported via
      NFS server
    - target can have a NFS client built into the kernel
    - very convenient for development, when there is no storage available yet

    On host:
    1. install an NFS server
    2. add the exported directory to the /etc/exports file and specify the client
       IP and options
    3. export by asking the NFS server to reload the file

    On target:
    1. the kernel needs to be built with NFS client support
    2. kernel must be booted with options to specify the target IP, the NFS server
       IP and details and other parameters...

  +-------------------------------+                +----------------------------+
  |                 Host          |                |                Target      |
  |                               |                |                            |
  |             NFS server        |                |             NFS client     |
  |                               |   Networking   |      built into the kernel |
  | /home/tux/rootfs/             |<-------------->| /                          |
  | /home/tux/rootfs/root/        |                | /root/                     |
  | /home/tux/rootfs/root/README  |                | /root/README               |
  | /home/tux/rootfs/usr/         |                | /usr/                      |
  | /home/tux/rootfs/usr/bin/     |                | /usr/bin/                  |
  | /home/tux/rootfs/bin/         |                | /bin/                      |
  | /home/tux/rootfs/bin/ls       |                | /bin/ls                    |
  +-------------------------------+                +----------------------------+

  Mounting rootfs from memory:
    - boot the system with a filesystem in memory: initramfs
    - either compressed CPIO archive integrated in the kernel image
    - or from an archived loaded into device memory
    - extracted at boot time
    - good for very fast booting because very small
    - good as intermediate step before switching to real rootfs

    Create external initramfs
    1. create a compressed CPIO archive
    2. include the archive in a Uboot container
    3. load the kernel binary, DTB and uInitramfs in RAM

    Also possible to have the kernel include a built-in initramfs
    1. config the kernel option to point to a directory or a cpio archive
       or to a file describing the contents
    2. make
    3. then the kernel image (zImage or bzImage) contains the kernel code/data
        and also the rootfs as a compressed cpio archive

  Root filesystem organization:
    - well defined by Filesystem Hierarchy Standard
      https://refspecs.linuxfoundation.org/fhs.shtml

    - /bin: basic programs

    - /boot: kernel images, configurations, initramfs (not common)

    - /dev: deice files

    - /etc: system-wide config

    - /home: user home directories

    - /lib: basic libraries

    - /media: mount points for removable media

    - /mnt: mount points for temporary mounted filesystem

    - /proc: mount points for the proc virtual filesystem,
        - exposes statistics about running processes, memory management, system
        params, etc.
        - contains one directory per running process
        - contains details about files opened by the process, CPU usage, etc.
        - /proc/interrupts, /proc/cmdline, /proc/cpuinfo are interesting

    - /root: home directory of root user

    - /run: runtime variable data

    - /sbin: basic system programs

    - /sys: mount point of the sysfs virtual system
        - sysfs represents the vision that the kernel has of buses, devices and
          drivers

    - /tmp: temporary files

    - /usr/bin: non-basic programs

    - /usr/lib: non-basic libs

    - /usr/sbin: non-basic system programs

    - /var: variable data files, for system services

  Basic applications:
    - in order to work, Linux needs a few applications:
      - an init: the first user space application started by the kernel
        responsible for starting all other user applications and services
        (in desktops = systemd)
      - a shell: to implement scripts, automate tasks or allow user interaction
      - basic unix executables: mv, cp, mkdir, cat, ls...
    - these components must be integrated in the root filesystem to make it usable

  Overall boot process:

  +--------------------------------------------------------------------------+
  |                                Bootloader                                |
  |             Loads the DTB and kernel to RAM, starts the kernel           |
  +--------------------------------------------------------------------------+
                                      |
                                      v
  +--------------------------------------------------------------------------+
  |                                  Kernel                                  |
  |               Initializes hardware devices and kernel subsystems         |
  |                Mounts the root filesystem indicated by root=             |
  |                 Starts the init application, /sbin/init by default       |
  +--------------------------------------------------------------------------+
                                      |
                                      v
  +--------------------------------------------------------------------------+
  |                                Rootfs                                    |
  |                                                                          |
  | +----------------------------------------------------------------------+ |
  | |                             /sbin/init                               | |
  | |             Starts other user space services and applications        | |
  | +----------------------------------+-----------------------------------+ |
  |                                    |                                     |
  |                  +-----------------+-----------------+                   |
  |                  |                                   |                   |
  |                  v                                   v                   |
  |        +-------------------+               +-------------------+         |
  |        |       Shell       |               |Other applications |         |
  |        +-------------------+               +-------------------+         |

7. BusyBox
-------------------------------------------------------------------------------

  Linux needs a basic set of programs:
  - init
  - shell
  - basic utilities

    In normal Linux, these are different projects... Lots of stuff to integrate.
    BusyBox is an integrated alternative solution, popular in embedded.

  https://www.busybox.net/

  BusyBox in the root filesystem:
  - all utilities are compiled into a single executable in /bin/busybox
  - all applications are symbolically linked to busybox
  - can be pretty small (<500KB)

  Can be configured similarly to Linux:
  - make defconfig : regular options
  - make allnoconfig : unselects all
  - make menuconfig : visual menu configuration
    - choose what commands to compile
    - choose which features is suppoted on each command

  Compiling BusyBox:
  1. set cross-compiler, as usual
  2. set the installation directory
  3. add the cross-compiler path to PATH
  4. compile with make
  5. install it : creates a UNIX directory structure with sym links to the executable

  Features:
  - includes an implementation of init program
    - single file
    - allows to configure what services start at startup, control shutdown...

7. Accessing hardware devices
-------------------------------------------------------------------------------

  Kernel Drivers:

      (example of a GPIO expander controlled by i2c)

      +-----------------------+     application accesses the standard kernel/
      |      Application      |     user-space interface via library or directly
      +-----------------------+     (see below)
          |             |
          v             |
      +---------+       |
      | Library |       |            e.g. libgiod
      +---------+       |
          |             |
          v             v
      =========================  Userspace
      Kernel/userspace interface     e.g. /dev/gpiochipXYZ
      =========================  Kernel
          |
          v
      +-----------------------+     exposes features of a certain class of devices
      |    Driver subsystem   |     through a standard kernel/user-space interface
      +-----------------------+     e.g. GPIO subsystem
          |
          v
      +-----------------------+     drives a particular devices connected to a bus
      |     Device driver     |     e.g. gpio-pca953x --> controls PCA9537 GPIO lines
      +-----------------------+
          |
          v
      +-----------------------+     provides API for drivers to access a bus
      |     Bus subsystem     |     e.g. I2C subsystem
      +-----------------------+
          |
          v
      +-----------------------+     drives an I2C, SPI, USB, PCI controller
      | Bus controller driver |     e.g. i2c-stm32f7 --> controls i2c controller in chip
      +-----------------------+

    - There are numerous kernel subsystems for device classes:
      - Networking stack over Ethernet, WiFi, CAN, etc.
      - GPIO
      - Video4Linux
      - DRM, GPU for video
      - ALSA for audio
      - PWM
      - Input for keyboard, mouse, etc.
      - Watchdog
      - RTC for real-time clocks
      - crypto for cryptography accelerators
      - remoteproc for auxiliary processors
      - ...

    - Possible to access device drivers from user-space
      - usually and preferrably, devices are controlled by a kernel driver
      - also possible to access devices from user-space through /dev/
      - useful for devices that do not fit in existing kernel subsystems
      - kernel provides: i2c-dev, spidev, UIO, libusb, sysfs for PCI
          e.g. https://docs.kernel.org/i2c/dev-interface.html

      - user-space drivers make an application less portable
      - user-space drivers make other kernel drivers not able to use the HW
        e.g. write a touchscreen driver in user-space: standard Linux graphics
             stack cannot use the touchscreen

    - Drivers upstream and out-of-stream:
      - upstream Linux kernel contains thousands of drivers
      - reviewed and approved by community
      - out-of-tree drivers are sometimes provided by device vendors
      - compatibility and quality issues
        - grep the Linux kernel tree to find kernel drivers
          e.g. https://elixir.bootlin.com/linux/v7.3/source/drivers/gpio/gpio-pca953x.c
          e.g. ~/embedded-linux-bbb-labs/kernel/linux$ git grep -i max7313
               then read the Makefile to learn what you need to enable
               need to enable CONFIG_GPIO_PCA953X


  User-space interfaces to drivers:

    1. device nodes in /dev
    2. entries in sysfs filesystem
    3. network sockets and related APIs

    Devices in /dev/:
    - most devices are presented through two abstractions:
      - character device: stream of bytes with no size, beginning or end
      - block device: composed of fixed-size blocks that can be read or written
    - internally identifiable via three informations (triplet):
      - type (character or block)
      - major (category of the device)
      - minor (identifier of the device)

    - ** everything is a file ** : devices can be manipulated with normal file APIs
      - device file:
        special type of file, stored in /dev/, exposes the triplet to user-space
        applications through a filename
      - example: /dev/ttyS0, /dev/tty1, /dev/sda ...

    - creating dev files:
      - done manually with "mknod" before Linux 2.6.32
      - devtmpfs is a virtual filesystem that can be mounted on /dev
      - kernel automatically creates and removes dev files from it
      - CONFIG_DEVTMPFS_MOUNT is the kernel option to automatically mount devtmpfs
        at boot time
      - other solutions: udev, mdev

    - Remember from before:
      "
          Linux makes system and kernel information available via pseudo-filesystems:
          - proc mounted on /proc: OS related info
          - sysfs mounted on /sys: system representation as a device tree
      "

      - all devices are visible in sysfs
        - /dev is usually to access the device
        - /sys usually only gives properties/information of the device
      - sysfs contains:

        ls /sys
          block  bus  class  dev  devices  firmware  fs  hypervisor  kernel  module  power

        - block/, symlinks to all block devices, in /sys/devices
        - bus/, one sub-folder by type of bus
        - class/, one sub-folder per class (category of devices): input, leds,
          pwm, etc.
        - dev/
          - block/, one symlink per block device, named after major/minor
          - char/, one symlink per character device, named after major/minor
        - devices/, all devices in the system, organized in a slightly chaotic
          way, see this article
        - firmware/, representation of firmware data
          - devicetree/, directory and file representation of Device Tree nodes
            and properties
        - fs/, properties related to filesystem drivers
        - kernel/, properties related to various kernel subsystems
        - module/, properties about kernel modules
        - power/, power-management related properties

        Example:
          - /sys/bus/i2c/drivers: all device drivers for devices on i2c buses
          - /sys/bus/i2c/devices: all devices on i2c buses
            - /sys/bus/i2c/devices/0-002a: one device, contains symlinks:
              - driver: symlink to driver directory /sys/bus/i2c/drivers
              - of_node: symlink to the directory for the DT node describing the device

            Cool example: echo 0 | sudo tee /sys/class/leds/tpacpi\:\:lid_logo_led/brightness

      - other virtual filesystems:
        - debugfs, mounted on /sys/kernel/debug
        - configfs, mounted on /sys/kernel/config

  Kernel Modules

    - Why?
      - keep the kernel minimal, load drivers on-demand depending on HW detected
      - driver development, modify, test, without rebooting

    - Files:
      - compiled kernel module is .ko (kernel object)
      - metada files modules.dep/.alias/.symbols/.builtin
        + each file has an optimized "bin" file
      - Installation in /lib/modules/<kernel-version>

    - Dependencies:
      - described in modules.dep and modules.dep.bin
      - some modules must be loaded before others

    - Aliases:
      - described in module.alias
      - allows to know which module to load based on different supported devices
